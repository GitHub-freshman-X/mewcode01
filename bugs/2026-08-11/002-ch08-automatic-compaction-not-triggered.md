# 真实 API 会话超过低窗口测试线后未触发自动压缩

## 状态

已澄清：自动压缩最终已触发，初始误判来自把一个 task 内多次 Provider 请求的累计输入量，当作单次自动决策的估算值。

## 用户可见现象

使用低窗口 `ch08-auto.yaml` 进行真实 API 人工测试时，TUI 显示单个任务累计 `tokens in: 18825`，随后继续发送最小消息，仍未显示 `automatic` 上下文压缩事件。

## 已知复现信息

- fixture 工作区：`/private/tmp/mewcode-ch08-manual.bX4qFp`。
- 连续以 `read_file` 读取约 3,633 字节的 `context-01.txt` 至 `context-04.txt`。
- 用户确认本次 context 文件未被第一层持久化；fixture 内存在的部分历史持久化文件来自此前不同测试会话，不能作为本问题的配置证据。
- 自动压缩仅在 `Runner` 每轮普通 Provider 请求前调用 `Manager.Decision`。

## 当前诊断

`tokens in` 是 TUI 对一个 task 内 Provider usage 的累计展示；自动决策使用最近一次请求的 `InputTokens` 锚点和锚点后的历史增量，二者不能直接等同。当前日志未记录有效的窗口配置、每轮估算值、自动线和决策结果，尚无法区分配置未生效、Provider usage 映射异常或估算/历史锚点错误。

已检查 fixture 的结构化日志：此前一个进程确实以 2,400 字符级第一层阈值持久化了四份 context 结果；后续两个进程没有任何持久化或第二层压缩事件。不同进程的持久化目录和日志不能混用推断当前会话配置。

代码确认：TUI 的 task 总用量会累加同一任务中“工具调用请求”和“工具结果后的最终回答请求”；而 `RecordUsage` 每轮都会用最后一次请求的用量覆盖锚点。因此即使 TUI 累计值为 18,825，最后一次请求及其后新增 assistant 文本仍可能低于 10,500 自动线。现有日志无法确认该假设。
