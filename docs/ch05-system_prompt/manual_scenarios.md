# MewCode System Prompt 人工对比场景

## 场景 1：编辑前读取

- 输入：要求修改一个已存在文件中的具体函数。
- 观察点：模型是否先调用读取文件工具，再提出或执行编辑。
- 期望行为：在任何写入或编辑前，先读取目标文件并基于实际内容行动。
- 失败信号：未读取文件就直接写入、猜测文件内容，或忽略工作区边界。

## 场景 2：搜索优先

- 输入：要求找到某个符号、配置项或错误信息的定义位置。
- 观察点：模型是否优先调用搜索代码或查找文件工具。
- 期望行为：使用搜索工具定位候选位置，再读取相关文件确认。
- 失败信号：只靠猜测路径回答，或在未定位上下文时直接修改文件。

## 场景 3：规划模式只读

- 输入：`/plan 添加一个新命令并补测试`。
- 观察点：请求工具集合是否仅包含只读工具，动态系统补充是否包含规划模式约束。
- 期望行为：模型只探索和输出计划，不写文件、不运行副作用命令。
- 失败信号：规划阶段请求写入、编辑、执行副作用命令，或把系统约束混入用户任务文本。

## 场景 4：`/do` 不受规划模式污染

- 输入：先执行一个 `/plan` 并得到计划，再执行 `/do`。
- 观察点：`/do` 请求是否恢复完整工具集合，动态系统补充是否为执行计划模式。
- 期望行为：`/do` 按顺序携带全部待执行计划，并可使用完整工具落地和验证。
- 失败信号：`/do` 仍携带规划模式只读约束、拒绝修改文件，或遗漏某个待执行计划。

## 场景 5：环境信息正确使用

- 输入：询问当前工作区、Shell、日期或要求根据可用工具完成任务。
- 观察点：模型是否依据动态环境补充中的工作区路径、操作系统、Shell、日期、模式和工具范围回答或行动。
- 期望行为：环境信息位于系统级动态补充中，不出现在用户可见历史；模型使用这些信息做出正确判断。
- 失败信号：模型声称不知道当前环境、引用过期日期，或把环境补充当作普通用户消息复述。
