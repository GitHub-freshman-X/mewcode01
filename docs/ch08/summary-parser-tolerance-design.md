# 第八章摘要标签容错设计

## 背景

真实 Provider 的自动摘要已触发，但模型返回多个 `<summary>` 开始标签。现有解析器严格拒绝多个标签，导致当前 Agent task 失败。

## 目标

保持压缩后 history 中只有一个语义明确的摘要，同时容忍模型在一次响应中重复生成多个完整摘要块。

## 方案

### 输出约束

保留“只返回一个非空 `<summary>...</summary>`”的要求，并在摘要请求的末尾再次强调：不得输出解释、Markdown、分析文本或第二个 summary 标签。提示词用于降低异常输出概率，但不作为解析正确性的唯一保障。

### 解析策略

解析器扫描响应中所有完整、非空、非嵌套的 `<summary>...</summary>` 候选块：

1. 仅有一个候选块时，保持当前成功语义。
2. 有多个候选块时，选择最后一个完整候选块作为正式摘要。
3. 所有其他候选块及标签外文本均被丢弃，绝不写入 history。
4. 缺少完整块、空块、嵌套标签、未闭合标签或候选摘要超过既有摘要输出预算时，解析失败，保持原历史不变。

选择最后一个块的理由是模型常先生成草稿或重复版本，最后一段通常是收束后的正式输出；但该规则只适用于结构完整的独立块，不拼接多个摘要。

### history 重建

`Rebuild` 的输入仍是单个纯摘要字符串。历史结构不变：一条边界消息（含选定摘要）加近期原文；不会出现多份摘要、XML 标签外说明或模型草稿。

### 可观测性

不为第八章向日志事件定义添加专用结构。`internal/logging` 提供通用的受限诊断载荷捕获能力：调用方传入 `kind`、内容和最大字符数，Logger 将截断后的内容保存为权限 `0600` 的诊断文件，并返回路径、原始大小、保存大小与截断标记。JSONL 仅记录这些元数据，绝不写入载荷正文。

上下文模块在摘要解析失败时，以 `context-summary-response` 作为 kind 调用该通用能力；它在既有动态 Fields 中记录解析错误、标签序列、响应长度和诊断文件引用。只有 `agent.context.debug_summary_response_chars` 大于零时才捕获正文，默认关闭。TUI 继续显示失败原因和诊断文件路径，不展示正文。

```yaml
agent:
  context:
    # 默认 0（关闭）；仅排障时设置小的正整数。
    debug_summary_response_chars: 4096
```

嵌套结构仅在外层完全是空白包装、且只包裹一个子 summary 时接受；实际摘要始终是最内层正文。外层含文字或多个子块时保持失败。

## 测试

- 一个完整 summary：原有行为不变。
- 两个完整 summary：仅返回第二个的正文。
- summary 前后有普通文本：普通文本不进入结果。
- 空候选、嵌套标签、缺闭合标签：返回错误，调用方不替换历史。
- Runner 自动压缩遇多个 summary：压缩成功、历史仅包含最后一个摘要、正常请求继续执行。
- 日志仅包含候选数量、长度与状态，不含摘要正文。
- 通用日志诊断捕获：截断、0600 权限、关闭时不创建文件，且不包含第八章专用逻辑。

## 非目标

- 不将多个摘要原封不动或拼接后写入 history。
- 不在本次改动引入 Provider 专属 JSON Schema/structured output；可另行评估为更强的长期方案。
- 不对摘要失败自动执行额外模型修复请求，避免增加成本和失败循环。
