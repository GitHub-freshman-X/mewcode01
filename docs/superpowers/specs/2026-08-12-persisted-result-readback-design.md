# 已持久化工具结果回读识别设计

## 背景

第八章的第一层上下文压缩会把超限工具结果写入会话专属文件。现有实现为了识别该文件的 `read_file` 回读结果，在内存中保存每个原始结果的完整内容，并以内容完全相等作为放行条件。

这会重复占用大结果的内存；当 `read_file` 因输出限制截断内容时，也无法匹配完整内容，导致回读结果可能再次被持久化。

## 目标

- 以已持久化文件的来源路径识别回读结果。
- 不再在 `ResultStore` 中复制保留完整工具结果内容。
- 对持久化文件的截断回读仍跳过第一层再次持久化。

## 设计

`ResultStore` 维护当前会话中由自身成功创建的、经 `filepath.Clean` 规范化后的绝对路径集合。

持久化成功后，`Persist` 将新文件路径登记到该集合。`isReadback` 仅处理工具名为 `read_file` 的成功结构化结果：解析返回 JSON 的 `data.path`，将其转换为规范绝对路径，并检查其是否存在于集合。命中时，`PrepareResults` 跳过该结果的单项和消息聚合持久化处理。

集合不是目录前缀匹配，也不接受任意 `.mew` 路径；只接受当前 `ResultStore` 已创建并登记的精确路径。

## 错误处理与边界

- JSON 不合法、缺少路径、相对路径无法解析或路径未登记：不视为回读，保留现有持久化策略。
- `read_file` 失败结果不视为回读。
- 不增加哈希校验：本次问题是识别来源而非检测内容篡改；哈希对截断内容无法完成完整性验证。
- 不修改 `read_file` 的大小或输出限制，也不新增分段读取接口。

## 测试

- 已持久化文件的正常 `read_file` JSON 回读不再次持久化。
- `data.content` 是被截断的前缀、但 `data.path` 指向已登记文件时，仍不再次持久化。
- 内容相同但路径未登记的 `read_file` 结果不获得豁免。
